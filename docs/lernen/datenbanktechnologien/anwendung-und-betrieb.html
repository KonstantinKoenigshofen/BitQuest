Welche Logik hat ihren Platz in der Datenbank?

Fachliche Regeln, die für alle schreibenden Programme gelten, sind im Schema gut aufgehoben. Eine Eindeutigkeitsbedingung schützt zum Beispiel auch beim Import und bei parallelen Zugriffen. Die Anwendung kann zusätzlich früh verständliche Fehlermeldungen geben. Wenn eine Regel als Constraint ausdrückbar ist, bleibt sie für künftige Datenbankzugriffe direkt sichtbar.

Sicht (view)
Eine benannte Abfrage stellt Spalten und Zeilen in einer gewünschten Form bereit. Sie kann eine stabile Leseschnittstelle oder eingeschränkte Sicht auf Daten bilden. Eine gewöhnliche View wird abgefragt, indem ihre zugrunde liegende Abfrage berücksichtigt wird. Eine materialisierte Sicht speichert ein Ergebnis, das nach einer festgelegten Strategie aktualisiert wird.
Sequenz (sequence)
Sie vergibt fortlaufend erzeugte Werte, etwa für technische Schlüssel. Lücken, etwa nach Abbrüchen, sind möglich. Prüfe eine fachliche Vorgabe nach lückenloser Nummerierung gesondert.
Trigger
Eine Datenbankroutine reagiert automatisch auf ein Ereignis wie INSERT oder UPDATE. Das eignet sich etwa für eine Änderungsprotokollierung. Berücksichtige indirekte Effekte bei Tests und Fehlersuche.
Gespeicherte Prozedur (stored procedure)
Ein explizit aufrufbarer Ablauf in der Datenbank bündelt mehrere Operationen. Das kann mehreren Anwendungen denselben Ablauf bereitstellen. Syntax, Transaktionsmöglichkeiten und Portabilität hängen vom System ab.

Was übernimmt die Anwendung beim Datenbankzugriff?

Die objektrelationale Abbildung (object–relational mapping, ORM) übersetzt zwischen Objektstrukturen und Tabellen. Ein ORM kann damit SQL aus Objektoperationen erzeugen. Kontrolliere die erzeugten Abfragen, etwa wenn zunächst eine Liste geladen wird und anschließend pro Objekt eine weitere Abfrage folgt (N+1 query problem). Wähle die Ladeform nach benötigten Daten und erwarteter Anzahl.

Die Anwendung entscheidet, welche Operationen gemeinsam bestätigt werden. Achte darauf, dass sie dieselbe Verbindung und Transaktionsgrenze verwenden. Übergebe Eingabewerte als gebundene Parameter und ordne Datenbankfehler fachlich ein. Eine Eindeutigkeitsverletzung kann etwa bedeuten, dass eine andere Anfrage denselben Schlüssel zuerst belegt hat.

Wie änderst du ein Schema im laufenden Betrieb?

Schemamigrationen sind versionierte Änderungen an Struktur und Daten. Wenn alte und neue Anwendungsstände gleichzeitig laufen können, ergänze zunächst kompatible Strukturen. Befülle zum Beispiel eine neue Spalte schrittweise und achte darauf, dass laufende Schreibvorgänge die neuen Daten ebenfalls korrekt halten. Stelle die Anwendung um und entferne die alte Spalte erst, wenn keine laufende Version sie mehr braucht.

Prüfe vorab mit realistischen Datenmengen die Dauer, Sperrwirkungen und die Integrität nach der Umstellung. Bei einem Rückweg muss die alte Anwendung auch mit bereits geschriebenen neuen Daten zurechtkommen. Plane bei destruktiven Änderungen eine getestete Wiederherstellung oder einen Weg zur Korrektur im neuen Stand.

Wer darf welche Daten wofür sehen oder ändern?

Vergib Rechte an Rollen nach ihren Aufgaben. Eine Auswertungsrolle braucht etwa Leserechte auf eine begrenzte Sicht. Die Anwendungsrolle braucht normalerweise keine Rechte, Tabellen zu löschen. Für Migrationen kannst du eine eigene Rolle verwenden. Prüfe Zugriffsrechte auch für Sicherungen, Protokolle und Datenexporte.

Speichere personenbezogene Daten nur für einen festgelegten Zweck und nur im benötigten Umfang. Bestimme, wann sie gelöscht werden und wie du Testsysteme, Exporte und Sicherungskopien behandelst. Trenne nach Möglichkeit Daten, die Personen identifizieren, von breiter genutzten Auswertungsdaten.

Woran erkennst du, ob eine Sicherung brauchbar ist?

Ein Backup ist eine Kopie für die Wiederherstellung. Ein Restore stellt Daten aus ihr wieder bereit. Unterstützt das System eine zeitpunktgenaue Wiederherstellung (point-in-time recovery), kannst du eine Basissicherung und passende Protokolle bis zu einem gewählten Zeitpunkt einspielen. So lässt sich zum Beispiel der Stand unmittelbar vor einem fehlerhaften Löschvorgang wiederherstellen.

Lege fest, wie viel Datenverlust vertretbar ist und wie lange ein Ausfall dauern darf. Teste in einer getrennten Umgebung, ob Daten vollständig lesbar sind, die Anwendung damit startet und die Wiederherstellung in der vorgesehenen Zeit gelingt.

Merksätze

  • Constraints schützen zentrale Regeln für alle Zugriffswege.
  • Anwendungen steuern Transaktionsgrenzen und sollten die tatsächlich ausgeführten Abfragen kennen.
  • Versioniere Migrationen, vergib Rechte nach Aufgaben und teste Wiederherstellung mit realistischen Daten.

Verständnisfrage

Eine selten genutzte Spalte soll entfernt werden, während zwei Anwendungsversionen parallel laufen. Wie gehst du vor?

Musterantwort

Prüfe Abhängigkeiten in Anwendung, Sichten und Abfragen. Entferne die Nutzung zuerst in einer neuen, noch kompatiblen Version und warte, bis sämtliche älteren Instanzen und Verbraucher umgestellt sind. Entferne die Spalte in einer separaten Migration mit geprüftem Wiederherstellungs- oder Korrekturweg. Dadurch können alte Instanzen die Spalte bis zu ihrer Ablösung weiter lesen.
