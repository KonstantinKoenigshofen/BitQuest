Was gehört in dieselbe Transaktion?

Eine Transaktion bündelt Anweisungen, die eine fachliche Änderung gemeinsam bilden. Wenn ein Lagerbestand sinkt und gleichzeitig ein Entnahmebeleg entsteht, gehören beide Änderungen zusammen, falls jeder Abgang einen Beleg braucht. Mit BEGIN öffnest du in PostgreSQL eine Transaktion, mit COMMIT schließt du sie erfolgreich ab. ROLLBACK verwirft ihre noch nicht bestätigten Änderungen. Bei Autocommit läuft jede einzelne Anweisung ohne expliziten Block typischerweise in ihrer eigenen Transaktion.

Atomarität (atomicity)
Alle Änderungen werden wirksam oder die Transaktion wird als Ganzes verworfen.
Konsistenz (consistency)
Ein gültiger Ausgangszustand führt wieder zu einem gültigen Zustand. Datenbank-Constraints prüfen nur Regeln, die im Schema definiert sind. Weitere Invarianten brauchen korrekte Transaktionslogik.
Isolation (isolation)
Sie bestimmt, welche parallelen Änderungen eine Transaktion bemerkt und welche Wechselwirkungen zulässig sind.
Dauerhaftigkeit (durability)
Bestätigte Änderungen überstehen Ausfälle im Rahmen der zugesagten Persistenz.

Halte eine Transaktion so kurz, wie die fachliche Regel erlaubt. Warte etwa außerhalb einer offenen Transaktion auf Benutzereingaben. Sonst bleiben Sperren oder alte Datenversionen womöglich länger als nötig gebunden.

Welche Beobachtungen können bei parallelem Lesen auftreten?

Dirty Read
B ändert einen Preis von 20 auf 25. A liest 25, bevor B bestätigt. B macht ein Rollback. A hat einen Wert verwendet, der nie bestätigt wurde.
Non-Repeatable Read
A liest einen Preis von 20. B setzt ihn auf 25 und bestätigt. A liest dieselbe Zeile erneut und sieht 25.
Phantom
A fragt alle offenen Tickets ab. B fügt ein weiteres offenes Ticket ein und bestätigt. Dieselbe Filterabfrage von A liefert nun eine zusätzliche Zeile.

Welche Isolation garantiert der SQL-Standard und welche PostgreSQL?

Die Stufen des SQL-Standards legen Mindestgarantien fest. READ UNCOMMITTED darf unbestätigte Änderungen zeigen. READ COMMITTED schließt Dirty Reads aus. REPEATABLE READ verhindert zusätzlich nicht wiederholbare Einzelzeilenlesungen, erlaubt als Mindestgarantie aber noch Phantome. Bei SERIALIZABLE müssen die Wirkungen erfolgreich abgeschlossener Transaktionen einer möglichen seriellen Reihenfolge entsprechen.

In PostgreSQL ist READ COMMITTED voreingestellt, und READ UNCOMMITTED verhält sich genauso. Ein normales SELECT erhält dabei zu Beginn jeder Anweisung eine aktuelle Sicht (snapshot). REPEATABLE READ verwendet für normale Abfragen eine Lesesicht ab der ersten Anweisung, die keine Transaktionssteuerung ist. Eigene Änderungen bleiben sichtbar. So bleiben auch vom anderen Prozess bestätigte Phantome unsichtbar.

Die Vertiefungsunterlage Performanz-Transaktion (Kap. 10, § 10.2, gedruckte S. 303–305) diskutiert die drei Leseanomalien. Für die Einstufung zählt zusätzlich die Serialisierungsanomalie. Bei PostgreSQLs REPEATABLE READ können etwa beide Transaktionen zwei aktive Geräte sehen und jeweils ein anderes deaktivieren. Danach wäre keines mehr aktiv, obwohl jede Transaktion für sich eines übrig gelassen hätte. SERIALIZABLE erkennt solche Konflikte und kann eine Transaktion abbrechen. Bei einem Serialisierungsfehler muss die Anwendung die gesamte Transaktion mit frischen Leseergebnissen wiederholen. PostgreSQL-18-Handbuch, § 13.2 „Transaction Isolation“

Wie verhinderst du ein verlorenes Update?

  1. A und B lesen unter PostgreSQLs READ COMMITTED denselben Bestand von 10.
  2. A zieht in der Anwendung 2 ab, schreibt die berechnete 8 und bestätigt.
  3. B zieht von seinen zuvor gelesenen 10 eine 3 ab, schreibt die berechnete 7 und bestätigt. Erwartet wäre 5. Die Wirkung von A ist verloren (lost update).

Wenn es um eine einzelne Zeile geht, drücke die Änderung möglichst als Operation auf dem aktuellen Wert aus. Das folgende Statement zieht nur ab, wenn ausreichend Bestand vorliegt. Prüfe, ob es eine Zeile geändert hat.

UPDATE lager
SET bestand = bestand - 3
WHERE id = 1 AND bestand >= 3;

PostgreSQL sperrt beim Schreiben die betroffene Zeile und prüft die Bedingung nach einem konkurrierenden Update anhand der aktualisierten Zeile erneut. Muss die Anwendung erst lesen und rechnen, kann sie die Zeile mit SELECT … FOR UPDATE in derselben Transaktion sperren. Bei Regeln über mehrere Zeilen musst du alle relevanten Wechselwirkungen berücksichtigen.

Wie steuert die Datenbank konkurrierende Zugriffe?

Sperren (locks) lassen kompatible Zugriffe zu und halten konfliktträchtige Zugriffe zurück. Beim Zwei-Phasen-Sperrprotokoll (two-phase locking, 2PL) nimmt eine Transaktion in der Wachstumsphase Sperren auf. Sobald sie mit der Freigabe beginnt, darf sie keine neuen Sperren anfordern. Mit geeigneten Sperren auf alle relevanten Daten oder Wertebereiche kann 2PL serialisierbare Abläufe gewährleisten. Wenn A auf B und B auf A wartet, liegt ein Deadlock vor. Eine Datenbank kann diesen durch Abbruch einer Transaktion auflösen.

Die Mehrversionenkontrolle (multiversion concurrency control, MVCC) hält mehrere Versionen einer Zeile. Eine Lesesicht bestimmt, welche Version sichtbar ist. So können gewöhnliche Lesezugriffe in PostgreSQL mit Schreibvorgängen überlappen. Konkurrierende Schreibzugriffe werden weiterhin koordiniert. Lange Transaktionen können die Bereinigung alter Versionen verzögern.

Merksätze

  • Transaktionsgrenzen folgen fachlichen Invarianten.
  • PostgreSQL bietet bei REPEATABLE READ eine stabile Sicht einschließlich Schutz vor Phantomen. Volle Serialisierbarkeit verlangt SERIALIZABLE.
  • Schreibkonflikte brauchen Schutz durch passende Updates, Sperren oder eine Isolationsstufe mit Wiederholung bei Konflikten.

Verständnisfrage

A liest offene Tickets, B fügt eines hinzu und bestätigt. Was sieht A bei einer zweiten gewöhnlichen SELECT-Abfrage in PostgreSQL unter READ COMMITTED und unter REPEATABLE READ?

Musterantwort

Unter READ COMMITTED kann A das neue Ticket sehen, weil die zweite Anweisung eine neue Lesesicht erhält. Unter REPEATABLE READ bleibt die ursprüngliche Sicht von A erhalten, sodass der von B eingefügte Treffer unsichtbar bleibt. Wenn A Entscheidungen anhand dieser Sicht trifft und gleichzeitig eigene Zeilen ändert, kann für fachliche Regeln über mehrere Zeilen trotzdem SERIALIZABLE nötig sein.
