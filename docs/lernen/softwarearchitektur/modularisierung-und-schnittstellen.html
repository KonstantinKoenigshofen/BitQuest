Was gehört in dasselbe Modul?

Eine Verantwortlichkeit (responsibility) beschreibt, welche Aufgabe ein Modul erfüllt und welche Regeln oder Daten es dabei betreut. Formuliere sie so, dass du für eine typische Änderung entscheiden kannst, wo sie hingehört.

Kohäsion (cohesion) bezeichnet den inneren Zusammenhalt. Regeln, die sich aus denselben fachlichen Gründen ändern, profitieren davon, nahe beieinander zu liegen. Bei der Prüfung einer Lieferadresse können beispielsweise die Regeln für Pflichtfelder und zulässige Kombinationen zusammengehören. Eine Sammlung aller Prüfungen im System hätte zwar einen gemeinsamen Namen, müsste aber aus vielen verschiedenen Gründen geändert werden.

Was verrät eine Abhängigkeit?

Kopplung (coupling) beschreibt, wie stark Teile aufeinander angewiesen sind. Sie entsteht auch ohne direkten Import, etwa wenn zwei Module dieselbe Tabelle beschreiben oder wenn eine Ablaufreihenfolge nur stillschweigend vorausgesetzt wird. Je stärker andere Teile von internen Details oder zeitlichen Zusagen abhängen, desto mehr Stellen können bei einer Änderung betroffen sein.

Die Abhängigkeitsrichtung (dependency direction) zeigt, welcher Teil den anderen kennen muss. Wenn Fachlogik direkt eine konkrete Datenbankbibliothek verwendet, muss sie beim Wechsel dieser Bibliothek gegebenenfalls mitgeändert werden. Bei der Abhängigkeitsumkehr (dependency inversion) beschreibt die Fachlogik ihren Speicherbedarf durch eine Schnittstelle. Der technische Baustein implementiert sie. Die Fachlogik ruft ihn zur Laufzeit auf, während im Code die Implementierung von der fachlich definierten Schnittstelle abhängt.

Prüfe den erwarteten Nutzen einer solchen Grenze. Für eine einfache, stabile Hilfsfunktion kostet eine zusätzliche Schnittstelle oft mehr Orientierung, als sie bei späteren Änderungen spart.

Was sollte eine Schnittstelle offenlegen?

Beim Verbergen interner Details (information hiding) bleibt verborgen, was sich innerhalb eines Moduls ändern können soll. Nach außen zeigt es die angebotenen Operationen und ihre Zusagen. Eine Schnittstelle zur Abfrage eines Lieferstatus kann beispielsweise vereinbarte Statuswerte liefern, während Datenbankschema und Berechnung intern bleiben.

Ein brauchbarer Vertrag macht klar, welche Eingaben gültig sind, was ein erfolgreicher Aufruf bewirkt und welche Fehler zu erwarten sind. Halte auch wichtige Zusagen wie die Reihenfolge oder Wiederholbarkeit von Aufrufen fest, wenn Nutzer der Schnittstelle davon abhängen. Zusätzliche öffentliche Felder und Operationen vergrößern die Fläche, die du bei Änderungen berücksichtigen musst.

Woran erkennst du eine tragfähige Modulgrenze?

  • Die Verantwortung ist klar benennbar. Ein typischer Änderungswunsch lässt sich einem Modul zuordnen.
  • Fachlich zusammengehörige Regeln bleiben beieinander. Häufige Änderungen berühren möglichst wenige öffentliche Verträge.
  • Andere Teile greifen über die vorgesehenen Schnittstellen zu. Geteilte Daten, stillschweigende Reihenfolgen und zyklische Abhängigkeiten verdienen besondere Aufmerksamkeit.
  • Die Schnittstelle lässt sich aus Sicht ihrer Nutzer testen. Ein Fehlerfall und eine typische spätere Änderung zeigen, ob ihre Zusagen ausreichen.

Merksätze

  • Hohe Kohäsion bündelt Regeln, die sich aus ähnlichen Gründen ändern.
  • Kopplung entsteht auch durch gemeinsame Daten oder Annahmen zur Reihenfolge.
  • Eine gute Schnittstelle schützt interne Details und macht die erwartbaren Ergebnisse und Fehler verständlich.

Verständnisfrage

Zwei Module schreiben dieselbe Tabelle. Warum sind sie auch dann gekoppelt, wenn sie sich gegenseitig nicht importieren?

Musterantwort

Beide verlassen sich auf dasselbe Schema und dieselben Regeln für gültige Änderungen. Eine Schemaänderung oder neue Fachregel kann beide Module treffen. Ein Modul als Eigentümer der Daten kann die Schreibregeln bündeln und erlaubte Änderungen über eine Schnittstelle anbieten.
